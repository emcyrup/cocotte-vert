# 公式LINE からの予約登録

入口は2つある。**主な入口はフォーム**で、文章での登録は補助として残してある。

| 送る言葉 | 返るもの |
|---|---|
| `予約登録`（本文なし） | 予約登録フォームを開くボタン |
| `予約登録 8/20 14時 田中花子 カット` | 読み取った内容の復唱と［登録］［やめる］ |

文章での読み取りは、お名前が当たらないことがある（表記ゆれ・わんちゃんの名前・
同姓の多いお店）。当たらないたびに送り直しになるため、**探して選べるフォームを
既定の入口にしてある**。文章で読み取れなかったときも、フォームのボタンを添えて返す。

## フォームから登録する（liff/staff-reserve.html）

```
スタッフ（LINE）      システム
「予約登録」        →  フォームを開くボタン
［フォームを開く］  →  LIFF：本人確認 → お客様を探して選ぶ → 内容を入れる
［登録する］        →  reservations に登録 → Slack へ新規予約通知
```

**AI は介在しない。** お客様はスタッフが選んで確定させるので、取り違えも送り直しも起きない。
下書き（`reservation_drafts`）も挟まず、そのまま予約にする。フォームで見て入れた内容が
そのまま登録されるため、あらためて復唱する意味がないため。

### お客様の探し方

飼い主様のお名前・お電話番号・**わんちゃんのお名前**のどれでも引ける。
現場ではわんちゃんの名前で覚えていることが多いため、そこから飼い主様へたどれるようにしてある。

| 入れたもの | 当たるもの |
|---|---|
| `田中` | 飼い主様のお名前の部分一致 |
| `ココ` | わんちゃんのお名前の部分一致 → その飼い主様 |
| `5678` / `090-1234` | お電話番号の部分一致（数字2桁以上のときだけ） |

候補には**わんちゃんのお名前**とお電話番号の**下4桁**を添える（全桁は出さない）。
1件に絞れても自動では選ばない。選ぶのは必ずスタッフ。

見つからなければ「新規で登録する」から、お名前だけでも登録できる。
お電話番号が既存のお客様と重なる場合は、新しく作らずその方に寄せる。

### 関門

スタッフ登録の画面と同じ（`src/http/staffGate.js`）。加えて、この画面は
**連携済みのスタッフならグループの参加確認を通らなくても使える**
（1:1 のトークから開くため。連携そのものが本人確認済みの証になっている）。

1. LINE の ID トークンをサーバーで検証する（クライアントの言う userId は使わない）
2. 連携済みスタッフか、スタッフ用グループの参加者であること

画面を飛ばして API を直接叩かれても、この2つを通らなければ登録できない。

## 文章から登録する

スタッフが公式LINE へ「予約登録 …」と送ると、Bot が読み取った内容を復唱し、
［登録］が押されたときだけ予約カレンダーに入る。

```
スタッフ（LINE）                       システム
「予約登録 8/20 14時 田中花子 カット」 →  Haiku で解釈 → 下書きを保存
                                      ←  内容を復唱し［登録］［やめる］
［登録］                              →  reservations に登録 → Slack へ新規予約通知
                                      ←  「予約を登録しました」
```

**その場では予約を作らない。** 文章は AI が読み取っているため、読み違えたまま入れると
お客様の予定として残ってしまう。必ず内容を見せて確かめてもらう（シフト変更の確定と同じ考え方）。

## 使える場所

2か所。どちらでも同じように使える。

| 場所 | 誰が使えるか |
|---|---|
| スタッフ用の LINE グループ | そのグループの発言（スタッフ通知先に設定済みのグループのみ） |
| Bot との 1:1 のトーク | **連携済みスタッフ**の発言のみ |

顧客の発言を予約として読み取らないよう、**接頭辞を必須**にしている。
`予約登録` / `予約追加` / `予約入力` / `新規予約` のいずれかで始まる発言だけが対象。

一覧の問い合わせ（[予約確認](staff-manual.md#スタッフ用のlineグループから予約を確認する)）と
紛れないよう、登録の判定を先に行う。「予約登録 明日14時 …」が「明日の予約」の問い合わせとして
読まれることはない。

## 書き方

**飼い主様のお名前・日付・時刻**が読み取れれば、文章の形は自由。

| 送る文の例 | 解釈される内容 |
|---|---|
| `予約登録 8/20 14時 田中花子 カット 担当佐藤` | 8/20 14:00 田中花子様／カット／佐藤 |
| `予約登録 明日10:00 山田 090-1234-5678 シャンプー` | 翌日 10:00 山田様／シャンプー |
| `予約登録 8/27 9時 山本さくら お泊まり 2時間` | 8/27 09:00／所要120分 |
| `予約登録 8/20 14時 田中花子 お泊まり 2泊` | 8/20 14:00 入室／8/22 退室予定 |
| `予約登録 8/20 14時 田中花子 お泊まり 8/22退室` | 同上（泊数は退室日から数える） |

- コース・担当・所要時間は任意。書かれていなければ「未定」で登録し、あとから画面で直せる
- 所要時間を書かなければ、コースに設定された所要時間に従う
- 担当は在職スタッフの名前と突き合わせる。**同名が複数いるときは担当未定**にする
  （別人を担当にすると予定が食い違うため）

読み取れないときは予約を作らず、書き方を案内して終わる。理由が分かるときは、
何を直せばよいかを先に伝える。

### 読み取らないと決めていること

安全側に倒す判断は、すべて「誤った予約が入るより、書き直してもらう方がよい」という理由による。

| 書かれ方 | 扱い |
|---|---|
| 「2時」など午前・午後が分からない時刻 | 営業時間（`STORE_OPEN_TIME`〜`STORE_CLOSE_TIME`）に収まる方に解釈する。収まる解釈が2つある、または1つも無ければ読み取らない |
| わんちゃんの名前だけ（`ココちゃん 8/20 14時`） | 読み取らず「飼い主様のお名前で送ってください」と返す |
| 1通に予約が2件以上 | 読み取らず「1件ずつ送ってください」と返す |
| 取り消し・変更の依頼 | 読み取らない（LINE からはできない。登録の返信でも画面から行うよう案内する） |

**わんちゃんの名前を受け付けない理由。** 顧客の突合は飼い主様のお名前で行うため、
わんちゃんの名前で登録すると「ココ」という飼い主様が新しく作られ、
本来の飼い主様には前々日確認が届かない。

モデルが人の名前だと判断してしまう場合に備え、**新しいお客様として入るときは確認画面に
「飼い主様のお名前かどうかご確認ください」と出す**。読み取り側と確認側の2段で防ぐ。

### お泊まり（宿泊）

- `date` / `time` は**お預かり（入室）の日時**。予約カレンダーにはこの時刻で入る
- 泊数（`2泊`）と退室日（`8/22退室`）はどちらの書き方でもよい。片方だけでももう一方を導く。
  食い違うときは**退室日を優先**する（日付の方が読み違いに気付きやすいため）
- 上限は 30泊。これを超える泊数・退室日は書き間違いとみなし、宿泊なしとして扱う
- 退室日は下書きの `checkout_date` に持ち、本予約にするとき
  **予約のメモ**へ「お泊まり 2泊（8月22日(土) 退室予定）」として残す
  （`reservations` に退室日の列は持たない。予約一覧の「ご要望・メモ」で見える）
- カレンダーの帯は入室日にだけ出る。複数日にまたがる帯にはしていない

## お客様の特定

1. **電話番号**が書かれていて一致すれば、その方（電話番号はこのシステムの突合キー）
2. なければ**お名前で完全一致**（姓名の間の空白は無視して比べる）
3. それも無ければ**部分一致**（「田中」で「田中花子」を引き当てる）

結果によって返すものが変わる。

| 結果 | Bot の返し方 |
|---|---|
| 1人に絞れた | そのまま内容の確認へ |
| 複数いる | 候補を並べて選ばせる（電話番号は**下4桁だけ**添える）。「新しいお客様として登録」も選べる |
| 誰もいない | 新しいお客様として登録する前提で内容の確認へ |

**同名が複数いるときに勝手に決めない。** 別のお客様の予定に入れてしまうと、
リマインドも誤った相手へ飛ぶため。

新しいお客様は**お名前だけでも登録できる**。ただし電話番号が無いとリマインド配信の突合が
できないため、登録後の返信で「店舗管理画面から追加してください」と促す。
書かれた電話番号が既存のお客様と重なる場合は、新しく作らずその方に寄せる。

## 下書き（reservation_drafts）

読み取った内容は `reservation_drafts` に置く。予約そのものは
`reservationService.createManual` を通して作る（予約の書き込みは必ずあのアダプタを経由する）。

| 状態 | 意味 |
|---|---|
| `pending` | 内容を返して、［登録］の返事を待っている |
| `registered` | 登録済み。`reservation_id` に予約番号が入る |
| `cancelled` | ［やめる］が押された |

守っていること。

- **送られてきた場所でしか動かせない。** 下書きの取得・更新はすべて `source_type` /
  `source_id` を条件に入れている。別のトークからボタンを押されても他人の下書きは動かない
- **二重に押されても2件入らない。** 先に下書きを `registered` へ倒し、取れたときだけ予約を作る。
  予約の作成に失敗したら `pending` へ戻すので、押し直せる
- **24時間で期限切れ。** 何日も前のボタンを押されて、意図しない予約が入るのを防ぐ
- **登録できなかったことは必ず伝える。** 黙って終わると、入っていない予約を入ったつもりで
  運用してしまう。本人へ返信し、Slack へも出す

## 登録したあと

- 予約カレンダーと予約一覧に `confirmed`（確定）で出る
- Slack へ「新規予約」が飛ぶ（既存の手入力予約と同じ通知）
- 2日前になれば前々日確認の対象になり、来店登録すれば7日後フォローの対象にもなる

取り消し・日時の変更は管理画面から行う。LINE からはできない。
