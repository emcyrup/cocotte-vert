## Phase 8 — スタッフ勤怠（シフト変更申請）（完了）

スタッフが公式LINE のトークへ自由な文章で送ると、シフト変更の申請として店長に届く。

- [x] `staff.line_user_id` と連携コード（`006_shift_requests.sql`）
- [x] 申請テーブル `shift_requests`（対象日・区分・時間帯・理由・**申請の原文**）
- [x] 申請文の解釈（Claude Haiku、`src/ai/parseShiftRequest.js`）
- [x] Webhook での振り分け（`src/webhook/events/staffShift.js`）
- [x] 承認・却下と本人への LINE 通知（`src/shifts/service.js`）
- [x] 店舗管理画面「スタッフ情報・シフト入力」への組み込み
- [x] 週次シフト表のデータ化（`007_shifts.sql`）。スタッフを追加すると行が増え、
      承認した申請は該当のマスへ反映される
- [x] スタッフ情報の照会・編集（名前・在職/退職・LINE ID の直接設定）
- [x] スタッフ用 LINE グループへの参加状況の表示
- [x] 申請内容を本人に復唱し、本人の「確定」でシフト表へ反映（`012_shift_request_held.sql`）。
      「保留」と答えたものだけ店長が判断する

**スタッフの識別**: LINE の userId は本人からは見えないため、連携は3通り用意した。
①スタッフ用グループで本人が「スタッフ登録 高橋」と名前を送る、②管理画面で発行した6桁の
合言葉を 1:1 で送る（有効期限24時間・使い捨て）、③管理画面で LINE ID を直接入力。
連携済みスタッフの 1:1 発言だけを申請として解釈するため、顧客の発言を巻き込まない。

**誤った申請を作らない**: 解釈に少しでも迷う場合、Haiku は申請を作らず書き直しを促す。
半休の午前・午後が不明、時刻の欠けた時間休なども申請にしない。承認画面には必ず原文を出す。

**確定は本人が行う**: 店長の承認を待つと反映が遅れるため、申請した本人が LINE 上で内容を
確かめて確定させる。AI の読み違いをそのまま入れないよう、復唱を必ず挟む。迷ったときの
逃げ道として「保留」を用意し、これだけが店長の判断に回る。

      これが主な入口
- [x] お客様の検索（飼い主様のお名前・お電話番号・**わんちゃんのお名前**のどれでも引ける）
- [x] 予約文の解釈（Claude Haiku、`src/ai/parseReservationEntry.js`）。文章での登録は補助扱い
- [x] お泊まりの泊数・退室日（退室日は予約のメモへ残す）
- [x] 下書きテーブル `reservation_drafts`（`013_reservation_drafts.sql`）
- [x] 顧客の突合（電話番号 → 名前の完全一致 → 部分一致）と、絞れないときの選択
- [x] 内容の復唱と［登録］［やめる］。本予約は `reservationService.createManual` を通す
- [x] スタッフ用グループと 1:1 の両方からの入口
- [x] お名前だけの新規のお客様の登録（電話番号の追加は画面へ誘導）

**顧客を勝手に決めない**: 同名が複数いるときは候補を並べて選ばせる。別のお客様の予定に
入れると、リマインドも誤った相手へ飛ぶため。電話番号は下4桁だけ添えて見分けられるようにした。

**入っていない予約を入ったつもりにさせない**: 下書きは送られてきた場所でしか動かせず、
二重に押されても1件しか入らない（先に下書きを押さえてから予約を作る）。作成に失敗したら
下書きを返事待ちへ戻し、本人と Slack の両方へ失敗を伝える。

**フォームを主な入口にした理由**: 文章での読み取りはお名前が当たらないことがあり、
そのたびに送り直しになっていた。フォームなら探して選ぶので、取り違えも送り直しも起きない。
現場ではわんちゃんの名前で覚えていることが多いため、そこから飼い主様へたどれるようにしてある。

**未対応**: LINE からの取り消し・日時変更。誤操作の影響が大きいため、画面からのみ行う。

詳細は [reservation-entry.md](reservation-entry.md)。

## Phase 12 — EPARK未反映チェックリスト（完了）

予約の入口をこのアプリへ寄せる一方、EPARK からもお客様が予約できる状態は続く。
こちらで入った予約の枠を EPARK 側で閉じ忘れると、同じ時間に別のお客様が入る。

- [x] `reservations.external_blocked_at`（反映が済んでいるか）
- [x] `src/reservations/externalBlock.js`（閉じる作業・開け直す作業の一覧と、済み・未済の記録）
- [x] `/api/admin/external-blocks`（一覧と消し込み）
- [x] 予約管理画面の「EPARK未反映」カード
- [x] 日時を変えたら未反映へ戻す（`updateManual`）

**自動では閉じない（閉じられない）**: EPARK には外部から予約枠を操作する口が無い。
閉じる作業そのものは手作業のままで、ここが持つのは「やった／まだ」だけ。
**やり忘れを画面に出すこと**が目的で、自動で何かを送るわけではない。

**開け直す作業も並べる**: 取り消したのに枠を閉じたままだと、その時間の予約を取り逃がす。
閉じ忘れと同じくらい起きるので、同じカードに2つ目の一覧として出す。

**チェックの向きは画面の申告で決めない**: 一覧を開いたあとに予約の状態が変われば、
押した時点で意味が変わる。どちらの向きの作業かは SQL の中で予約の状態から決める。

**取り込んだ予約は対象外**: `external_id` が付いた予約はもともと EPARK 側にあるので、
閉じる必要がない。過ぎた予約も出さない（いま枠を閉じても意味がない）。

**いまは自動化が消し込む**: Phase 13 で自動反映を入れたので、このカードに残るのは
**自動で処理できなかった分だけ**になった。安全網としてのカード自体は残す。

**即時反映はアプリから直接ではない**: 本番サーバーには sudo が無く Chromium を置けないため、
ブラウザがあるのは GitHub Actions だけ。予約が動いたらアプリが**向こうを起こす**形にした
（起動から反映まで1〜2分）。**モードは渡さない**ので、live かどうかの判断は向こうの設定に
1本化されたまま。起こせなくても予約は通り、定期実行（30分ごと）が拾う。

**EPARK の予約は店舗の承認制**: 枠を閉じ忘れても二重予約そのものは起きない（断ればよい）。
自動化の目的は事故防止ではなく、無駄なリクエストと断りの手間を減らすこと。
**この前提が失敗時の許容度を決める**。静かに壊れても「EPARK の空きが実態とずれる」だけで、
今の運用に戻るにとどまる。だから RPA を試す価値がある。

**書いたら必ず読み直す**: 自動化で一番怖いのは「閉じたつもりで閉じていない」状態。
自動化されている前提で誰も見なくなるため、チェックリストより危険になる。
画面から読み直して意図どおりだったときだけ済みにし、確認できなければ済みにしない。

**安全網は残す**: 自動化は Phase 12 のチェックリストを消し込むだけ。失敗した分は画面に残り、
Slack にも飛ぶ。手作業の経路を消さないので、自動化が止まってもその日の運用は続く。

**既定は `off`**: 相手の画面を書き換える操作なので、送信系（`dry_run` 既定）よりさらに手前、
「一切触らない」を既定に置く。

**「閉じる」機能は無い。仮受付で埋める**: 実物の管理画面には予約枠を閉じる機能が無く、
枠に「仮受付」を入れて埋めるのが実際の運用だった。自動化もそれに倣う。
枠のチェックを入れて「仮受付」＝閉じる、「キャンセル」＝開ける。

**押す場所はコードに書かない**: 相手の都合で変わるものは `config/epark-profile.json` に
外出しした。**CSV の列の対応づけと同じ理由**。`{timeCompact}` や `{line}` が入っていない
セレクタは起動前に弾く（その日の枠を丸ごと、あるいは別の列まで掴んでしまうため）。
管理画面の URL には店舗の識別子が入るので `{base}` と書き、`.env` から差し込む。

**またがる枠を全部閉じる**: 相手は1時間刻み、こちらの予約は所要時間がまちまち。
90分なら2枠。1枠だけだと、はみ出した時間に別のお客様が入れる。

**開け直すのは自分が入れた仮受付だけ**: 本物のご予約には仮受付の印が付かない。
印が無い枠には絶対に触らない（こちらの取消と入れ違いで EPARK からご予約が入っていることが
ある）。コースからラインを決められないときも、勝手に閉じずに人へ回す。

**確認画面が出ない**: 「仮受付」を押しても確認ダイアログは出ない（実物で確認）。
押せたかどうかを教えてくれるものが無いので、手順の最後に「その枠が変わるまで待つ」を置き、
さらに画面を開き直して読み直す。変わっていなければ失敗としてチェックリストに残す。
**手順が転んでも読み直す**: 実物では「仮受付は入ったのに、入ったことを待ち構えるほうが
時間切れ」という転び方をした。押す前にその枠が「開」だと確かめてあるので、あとで「閉」に
なっていれば自分が閉じたもの。判断は例外の有無ではなく画面の状態で行う。

**押す場所は見た目の要素**: 実物のチェックボックスは `<label>` の中で CSS に隠されていて、
見えているのは `<span class="box">` のほう。`input` を直接押そうとすると時間切れになる
（実物で踏んだ）。`label` を押す。

**顧客情報の欄は埋めない**: 一覧にお名前を出したくて姓・名・電話番号を入れてみたが、
**実物ではお客様の欄を埋めると「仮受付」ではなくなり、ボタンが `disabled` になる**。
押せないまま終わるので、**名前も院内メモも入らずに無名の仮受付へ落ちていた**。
何も入力しなければ仮受付できる／受付内容を選ぶと仮受付が消える、というのが実物の決まりで、
お客様の欄も同じ扱いだった。名前を一覧に出すには「受付」を押すしかなく、それは取り消せない。
**院内メモだけを使う。**

**見分けは受付番号で**: もともとは仮受付の印（`li.tentative-reservation`）だけで自分の枠を
見分けていた。閉じたときに枠が持つ EPARK の受付番号を控えておき、開け直すときに一致する枠
だけを取り消す形に変えてある。番号は1件ごとに違うので、スタッフが手作業で入れた仮受付とも
区別できる。印より確実。番号を控えていない枠（この仕組みより前に閉じたもの）は、従来どおり
印で見分ける。

**キャンセルの確認は画面の中の小窓**: ブラウザの確認画面ではなく、ページに描かれた小窓
（`確認 / 受付をキャンセルします。よろしいですか？ / OK・キャンセル`）。自動操作の
「確認画面に答える」仕掛けでは越えられず、OK を押しに行く必要があった。

**重なっている予約の枠は開けない**: 予約は重なる。取消の 13:30-14:30 を開け直すとき、
14:00 を別の確定予約が使っていることがある。開けるとそのご予約のぶんの枠まで空き、しかも
その予約は「反映済み」のままなので誰も気付けない。同じ日の他の確定予約が使っている枠は
閉じたまま残す。ラインを決められないときは触らない側に倒す。

**自分が閉じた枠しか開けない**: スタッフも同じ画面で手作業の仮受付を入れている
（お昼休み・貸切など）。閉じにいった枠がすでに閉じていれば飛ばすが、そのまま取消のときに
開けると、スタッフが意図して止めていた枠を勝手に開けてしまう。実際に閉じた枠を
`external_blocked_cells` に残し、開け直すのはそこだけにした。

**実物が見られないので作り物で確かめた**: `test/fixtures/eparkFake.js` に実物の HTML の
作りを写した受付表を立て、実際の Chromium で駆動部を動かしている。実物に合わせるのは
設定であって、ログイン → 日付の受付表 → 押す → 読み直す、という流れは変わらない。

**枠が見つからないときは例外にする**: 「見つからない＝閉じている」と読むと、日付違いや
画面変更を成功と誤読して消し込んでしまう。分からないときは分からないと言う。

**仮受付にお名前を載せる**: 無名の仮受付では、EPARK の受付表を見ても誰のご予約か分からず、
結局こちらの画面と突き合わせる手間が残る。空き枠から開く「顧客検索及び新規受付登録」の
**院内メモ**に、お名前・ペット・電話番号・コース・予約番号の1行を入れる。
ただし **EPARK 側の顧客台帳は検索も選択も新規登録もしない**。同姓同名で別のお客様に
紐づけると相手の台帳が壊れて戻せない。メモに書くだけなら消せる。
押すのも「受付」ではなく**「仮受付」のまま**にする。仮受付の印が消えると、取消のときに
自分が入れた分を見分けられなくなり、安全網が丸ごと効かなくなるため。
開いた登録画面が本当にその枠のものかを hidden の日付・時刻・ラインで確かめてから押し、
途中で躓いたら**これまでどおりの無名の仮受付に落として枠だけ押さえる**。
`EPARK_DETAILS=off` で無名に戻せる。

**動かす場所は GitHub Actions**: 本番の AWS は sudo なし・Docker なし、検証環境の
Docker イメージにも Chromium は入れていない。**手元の PC を含め、どこにもブラウザが無い**。
ランナーには一式そろっているので、まず点検（`epark-check`）をそこから流せるようにした。
本番運用も同じ場所から定期実行するのが素直。サーバーには何も足さずに済む。

詳細は [import-api.md](import-api.md)。

いちばん質が悪い（画面には「写真は任意」と出るのに投稿できない）。`photoRequiredFor()` を
唯一の出どころにし、知らない投稿先は「要る」に倒した。

お知らせは事実そのものなので、ふくらませた分がそのまま誤報になる。
URL も一字一句そのまま残させる（短縮も言い換えもさせない）。

**リンクはこちらで作る**: WordPress は本文中の裸の URL を既定ではリンクにしない
（`make_clickable` は本文の既定フィルタに入っていない）。変換は**エスケープした後**に掛ける
── 先に掛けると、作った `<a>` ごとエスケープされてタグが文字として出る。
実体参照（`&quot;` など）から先は URL として扱わないので、本文に HTML を書かれても
href から抜け出せない。

**下書きであることは変えない**: 写真なしでも、スタッフが読んでから投稿する前提は同じ。
