# セキュリティ

このシステムは**お客様の氏名・電話番号・誕生日**を持ち、管理画面から**お客様へ LINE を送れる**。
守りの要点と、環境ごとに確かめることをまとめる。

> このリポジトリは公開設定。**ホスト名・IP・認証情報はここに書かない。**

---

## 守り方（コード側・全環境共通）

| 脅威 | 守り | 場所 |
|---|---|---|
| 画面に埋め込まれたスクリプト（XSS） | `innerHTML` に入れる値は必ず `esc()` を通す | `src/mock/index.html` |
| 他サイトからの操作（CSRF） | 管理 API への書き込みは、管理画面（同じオリジン）かブラウザ以外からだけ受け付ける | `src/http/security.js` |
| 枠への埋め込み（クリックジャッキング） | 管理画面は `X-Frame-Options: DENY` / `frame-ancestors 'none'` | `src/http/security.js` |
| SQL インジェクション | パラメータ化クエリのみ（`${}` の埋め込みは定数の列名だけ） | 全 SQL |
| なりすまし（LIFF） | LINE の ID トークンをサーバーで検証。画面の申告は使わない | `src/line/verifyIdToken.js` |
| Webhook の偽装 | LINE の署名を検証 | `@line/bot-sdk` の middleware |
| 管理画面の総当たり・時間差 | 固定長ハッシュで比較（長さで早く返さない） | `src/http/auth.js` |
| 写真の差し替え | JPEG の先頭バイトを確認、推測できない名前で保存、`nosniff` | `src/http/snsRoutes.js` |
| 依存ライブラリ | `npm audit` で 0 件を保つ | `package-lock.json` |
| GitHub Actions の乗っ取り | `GITHUB_TOKEN` は読み取りのみ | `.github/workflows/*.yml` |

### XSS（いちばん起きやすい）

お客様は LIFF の登録フォーム・予約フォームで**名前やご要望を自由に書ける**。LINE の表示名も
そのまま顧客名に入る。これを管理画面が `innerHTML` でそのまま描くと、スタッフが一覧や
カレンダーを開いた瞬間に、**そのお客様が書いたスクリプトが管理者の画面で動く**。
管理画面でできること（全顧客の持ち出し、予約の承認＝お客様への LINE 送信）は全部できてしまう。

2026-10 の診断で**12の欄**（顧客名・ペット名/犬種/メモ・予約のお客様名/コース/ご要望/担当・
シフト申請の名前/原文/理由・スタッフ名）がこの状態だったのを修正した。
`test/adminXss.test.js` が、各欄に HTML を入れて画面を一通り開き、スクリプトが1つも
動かないことを見張っている（ブラウザが要るので CI では飛び、手元で走る）。

**値が外から来るかどうかで判断しない。** 「スタッフしか入れない」欄も、スタッフの LINE が
乗っ取られれば外から来る。数値とコード内の定数以外は、全部 `esc()` を通す。

### CSRF

管理 API は Basic 認証。ブラウザは一度入力した Basic 認証を、**別のサイトから送られた
リクエストにも自動で付ける**（Cookie の SameSite のような仕組みが無い）。
ブラウザが付ける `Sec-Fetch-Site` を見て、`same-origin`（管理画面）と、ヘッダの無いもの
（curl・GitHub Actions からの EPARK 反映）だけを通す。

Origin と Host を比べる方法は採らない。本番の Nginx は管理会社の持ち物で、Host を転送して
いるか確かめられず、外れると管理画面が使えなくなるため。

## 環境ごとに確かめること

### 本番（AWS・管理会社の共用サーバー）

ここからは届かないので、手元またはサーバー上で確かめる。

**① 平文の待ち受けポートが外に開いていないか（最優先）**

アプリは `0.0.0.0:8017` で待ち受けている（平文の HTTP）。サーバーのファイアウォールで
外から届くと、HTTPS（Nginx）を通らずに管理画面へ届き、**パスワードが暗号化されずに流れる**。

```bash
# 自分の PC から。応答が返ってきたら開いている
curl -m 5 http://<本番サーバーの IP>:8017/health
```

- 応答が返る → 管理会社に、8017 番を Nginx からだけ受け付けるよう依頼する。
  Nginx が同じサーバーにあるなら、`.env` に `HOST=127.0.0.1` を足して再起動するだけでも塞がる
- タイムアウトする → 問題なし

**② サーバー上の確認**

```bash
node -v                    # 22 系の最新か（Node 本体にも脆弱性の修正が出る）
ls -l ~/cocotte-vert/.env  # -rw------- （600）になっているか
```

**③ デプロイのホスト鍵を固定する** — `PROD_VM_KNOWN_HOSTS`（[deploy-aws.md](deploy-aws.md) の手順8）

**④ データベースのパスワード** — 一度チャットに貼られたことがあるため、変更を推奨（管理会社へ依頼）。

### 検証環境（GCP・停止中）

停止中のため、外からは届かない。**ディスクには顧客データが残っている**ので、
削除するときはスナップショットも含めて消す（スナップショットにも同じデータが入る）。

移行のときに、悪意のある文字列が保存されていないか一度見ておく。
修正後の画面では文字として表示されるので害は無いが、入っていれば狙われていた証拠になる。

```sql
SELECT id FROM customers    WHERE name  ~ '[<>]';
SELECT id FROM pets         WHERE name  ~ '[<>]' OR breed ~ '[<>]' OR notes ~ '[<>]';
SELECT id FROM reservations WHERE note  ~ '[<>]' OR menu  ~ '[<>]';
```

### GitHub

- 公開リポジトリ。**git の履歴に秘密情報が入っていないことを確認済み**（2026-10）
- 検証環境を削除したら、使わなくなった Secret（`VM_HOST` / `VM_USER` / `VM_SSH_KEY`）も消す
- Settings → Code security で **Dependabot alerts** を有効にしておくと、依存ライブラリの
  脆弱性が見つかったときに知らせが来る
